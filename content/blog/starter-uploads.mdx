---
title: Uploads in dimah-starter go through dimah-s3
description: Avatars, logos, and other files in the starter are direct-to-bucket uploads. dimah-starter does not proxy the file.
date: 2026-11-19
tags: [dimah-starter, dimah-s3]
---

[dimah-starter](https://starter.dimah.dev) needs uploads for avatars and organization logos. I did not give it a second storage stack. The storage package is a thin use of [dimah-s3](https://s3.dimah.dev): the server signs a ticket, the browser sends the file to any S3-compatible bucket, and a Server Action stores the public URL.

The application starts with no S3 settings. Only the upload paths need a bucket. When they are configured, the bucket has to allow `GET`, `PUT`, and `HEAD` from the app's origin, and objects are served from `S3_PUBLIC_BASE_URL`.

An upload that was signed and never confirmed should not stay behind. The repository's production notes say to schedule `pnpm storage:purge` hourly so those objects leave the bucket and the database. Upload quotas are part of the same server-side rules. dimah-s3 expects auth, quotas, and database rules in server hooks, not in the browser.

That is the whole connection between the two projects. dimah-s3 does not know about organizations or Better Auth. dimah-starter does not know how to sign an S3 request. The starter calls the toolkit, then keeps the URL on the account or the organization the action already authorized.

Why the toolkit signs on the server is in [dimah-s3 signs the upload, then steps aside](/blog/presign-first). The repositories are [dimah-kz/dimah-starter](https://github.com/dimah-kz/dimah-starter) and [dimah-kz/dimah-s3](https://github.com/dimah-kz/dimah-s3).
