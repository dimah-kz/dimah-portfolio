[dimah-starter](https://starter.dimah.dev) needs uploads for profile avatars and organization logos. Instead of building a second storage layer, its `storage` package is a thin layer over [dimah-s3](https://s3.dimah.dev).

## The flow

The server signs a ticket, the browser sends the file to any S3-compatible bucket, and a Server Action saves the URL. When a new file replaces an old one, the action deletes the old file after the response has been sent.

## Configuration

The app runs without any S3 settings; only the upload paths need a bucket. Once you set `DIMAH_S3_SECRET` and the `S3_*` variables, the bucket's CORS has to allow `GET`, `PUT`, and `HEAD` from the app's origin, and files are served from `S3_PUBLIC_BASE_URL`.

## Cleaning up

A file that was signed but never confirmed should not stay in the bucket. Run `pnpm storage:purge` hourly, and those files leave both the bucket and the database. The repository ships a GitHub Actions workflow that does it once you add its secrets.

Upload quotas follow the same rule as everything else in the starter: they are enforced on the server, never in the browser.

## Two projects, one boundary

dimah-s3 knows nothing about organizations or Better Auth, and dimah-starter knows nothing about signing an S3 request. The starter calls the toolkit, then stores the URL on the account or organization that the action has already authorized.

Why the toolkit signs on the server in the first place is the subject of [dimah-s3 signs the upload, then steps aside](/blog/presign-first).
