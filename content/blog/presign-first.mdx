File uploads end up inside the application process more often than they should. The browser posts the file to your server, the server streams it on to S3, and a function stays open for as long as the transfer takes. [dimah-s3](https://s3.dimah.dev) takes your server out of that path.

## How an upload works

1. The browser asks to upload to a route. It sends the route's name, never an object key or a credential.
2. The server runs that route's guards, such as auth and quotas, and chooses a key inside the route's namespace.
3. It returns a short-lived signed URL, along with a signed upload ticket.
4. The browser sends the file straight to the bucket.
5. On confirm, the server checks the stored object with `HeadObject` before your `onConfirmed` hook runs.

The access key stays on the server the whole time. The server makes every decision, and the bucket moves the bytes. Because later calls carry only the ticket, the browser cannot swap the key, the route, or the size halfway through.

## Not an SDK wrapper

dimah-s3 covers upload, download, and delete, including resumable multipart uploads. Downloads use a signed URL, or pass through your server as a file proxy. List, copy, tagging, and other operations stay in your own code with `@aws-sdk/client-s3`.

It works with Amazon S3, Cloudflare R2, MinIO, ArvanCloud, and other S3-compatible stores: you pass in an `S3Client` configured for the provider.

## What you install

The server routes are the core. In React, the pieces are headless hooks. The shadcn UI, database tracking with folders, and share links are optional, and you can sign an upload without any of them.

To start a new app:

```bash
npx @dimah-s3/cli create my-app
```

To add it to an existing one, follow the [Quickstart](https://s3.dimah.dev/docs/quickstart). Version 1.x is no longer maintained, and the [upgrade guide](https://s3.dimah.dev/docs/migration-2-0) covers the move to 2.0. The source is at [dimah-kz/dimah-s3](https://github.com/dimah-kz/dimah-s3).
